# Lusyへのオンボーディング

このガイドは、Lusyに参加したい人がPRを作るための手順です。通常の申請ではTerraformを編集する必要はありません。

## 参加前に用意するもの

- 自分のGitHubアカウント。
- 自分のDiscordアカウントと、対象サーバーへの参加。
- 希望するロールと、参加を相談したLusyの担当者。

Discordサーバーへの参加は自動化されていません。招待URLはLusyの担当者から受け取り、先にサーバーに参加してください。

## 1. DiscordのユーザーIDを確認する

Discordのユーザー設定で開発者モードを有効にし、自分のプロフィールからユーザーIDをコピーします。設定画面の表示位置はDiscordのバージョンによって異なる場合があります。

表示名、ユーザー名、サーバーID、ロールIDとは別の値です。長い数字は**文字列としてダブルクォートで囲んで**YAMLに記入します。

## 2. 自分のファイルを追加する

`examples/alice.yaml`をコピーし、`members/<小文字のGitHubユーザー名>.yaml`を作成します。たとえばユーザー名が`alice`なら、ファイル名は`members/alice.yaml`です。

```yaml
github_username: alice
github_org_role: member
discord_user_id: "123456789012345678"
roles:
  - lusy
  - lumos-web
```

例のアカウント情報は、自分のものに置き換えてください。

| フィールド | 記入する内容 |
| --- | --- |
| `github_username` | 小文字のGitHubユーザー名。ファイル名と一致させる |
| `github_org_role` | 通常は`member`。`admin`はOrganization全体の所有者権限なので、管理者の指示がある場合だけ指定する |
| `discord_user_id` | コピーした自分のDiscordユーザーID |
| `roles` | 共通の`lusy`と担当プロジェクトのロール。Web開発の場合は`["lusy", "lumos-web"]` |

- `lusy`：GitHubの`Lusy`チームへの所属。
- `lumos-web`：GitHubの`[Lusy] Lumos Web`チームへの所属とDiscordの`Lumos Web`ロール。
- `lumos-discord-bot`：GitHubの`[Lusy] Lumos Discord Bot`チームへの所属とDiscordの`Discord Bot`ロール。

複数のプロジェクトを担当する場合は、それぞれのロールを追加します。付与先のIDやチーム名は[ロール一覧](../config/roles.yaml)で確認できます。

登録後は、この定義にない既存のGitHubチームへの直接所属とDiscordロールも取り消し対象です。Lusy以外で必要な権限がある場合も、管理者と相談してロール一覧に含めてください。Discordの`@everyone`と連携サービス管理ロール、GitHubの子チーム経由の継承所属は対象外です。

一つのファイルに複数人を書いたり、秘密鍵・Botトークン・メールアドレスなど申請に不要な情報を入れたりしないでください。公開リポジトリの場合、ユーザーIDの対応も公開されます。

## 3. PRを作成する

書き込み権限がなければForkからPRを作成します。非公開リポジトリでアクセスできない場合は、担当者にアクセスの付与または代理申請を依頼してください。

PR本文には以下を記入します。

- 自分のGitHubユーザー名とDiscordユーザーID。
- 希望するロール。
- 参加理由と、参加を相談した担当者。

タイトル例：`aliceのLusy参加申請`

通常の参加申請では、自分のメンバーファイルだけを変更します。ロール一覧やワークフローを変更する必要がある場合は、担当者に相談してください。

## 4. 検証とレビューを受ける

`Validate`が、ファイル形式、IDの重複、未知のロール、Terraform構成を確認します。失敗した場合はActionsのエラーメッセージに従って修正します。

管理者は、GitHubとDiscordのアカウントが申請者本人のものか、希望する権限が適切かを確認します。ファイルに書かれたIDだけでは本人確認は完了しません。

ReadyなPRでは[plan](operations.md#マージ前のprでplanを確認する)が自動実行されます。tfcmtのコメントで、対象コミットと追加・変更・削除される権限を確認してください。実際の適用はマージ後に行います。

追加コミット後はplanが自動的に再実行され、PRのレビュー承認が取り消されることがあります。検証とレビューが完了すると、管理者が`main`にマージします。

## 5. 招待を承諾し、アクセスを確認する

マージ後、管理者がApplyを手動起動し、Environmentで承認します。`Apply`が成功したら、次を確認してください。

- GitHub Organizationへの招待が届いた場合は承諾する。
- 申請したGitHubチームに所属できている。
- 申請したDiscordロールが付いている。
- 担当者から案内されたリポジトリやチャンネルを利用できる。

GitHubの招待は本人が承諾するまで有効になりません。チーム所属も招待承諾後に有効になります。

## うまくいかないとき

| 状況 | 確認すること |
| --- | --- |
| PRを承認されたが権限が付かない | PRがマージ済みか、管理者がApplyを起動・承認したか、`Apply`が成功しているか |
| GitHubに参加できない | 招待が届いているか、承諾済みか |
| Discordロールが付かない | 正しいユーザーIDか、サーバーに参加済みか。Botの問題は管理者に連絡する |
| Validateが失敗する | ファイル名が小文字のGitHubユーザー名と一致するか、IDが文字列か、ロール名が正しいか |

自分でPRを何度も作り直す必要はありません。担当者にPRと失敗したActions実行へのリンクを伝えてください。

## 権限変更・退会

ロールを変更するときも、自分のファイルを変更するPRを作成します。**ファイル削除はLusyだけでなく、GitHub Organization全体からの脱退も意味します。** Lumosの別チームに残る場合は、削除せずに管理者へ相談してください。

詳しくは[運用ガイド](operations.md)を参照してください。
